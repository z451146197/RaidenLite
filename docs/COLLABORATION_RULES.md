# RaidenLite 并行开发纪律

本文件用于 1 / 2 / 3 线以及后续 Codex / ChatGPT / 其他代理并行开发时统一操作方式。目标：允许高并发，同时避免 Cocos Creator 序列化文件互相覆盖。

## 1. Git 分支纪律（必须遵守）

- `main` 只作为可集成、可验证的基线，不作为并行开发工作区。
- 每条工作线必须在独立 `feature/*`、`fix/*`、`assets/*`、`docs/*` 分支提交。
- 开工前先读取最新 `main`；准备合并前再次同步/比较最新 `main`。
- 禁止为了省事直接 force-push `main`。
- 一个任务一个分支；任务完成后通过 PR 或明确的集成步骤进入 `main`。
- 合并成功后，其他仍在工作的分支应以新的 `main` 为下一轮基线，避免长期漂移。

## 2. Cocos 高冲突文件规则

以下文件/类型默认视为“单写者资源”：

- `*.scene`
- `*.prefab`
- `*.meta`
- `GameManager.ts`
- `Mission01Timeline.ts`
- 会大面积改动资源 UUID / 节点层级 /序列化引用的文件

并行开发时：

- 同一时段尽量只允许一条线修改同一个 `.scene/.prefab/.meta`。
- 其他线优先新增独立脚本、组件、工具函数或数据文件，再由负责场景集成的工作线接入。
- 遇到序列化冲突，不允许“保留双方全部内容”式盲合；必须确认 UUID、组件顺序、节点引用是否仍有效。

## 3. 推荐职责边界

当前 Mission 01 阶段推荐：

- **1 线：核心运行 / Gameplay** — 玩家、敌人、碰撞、Power、Bomb、局内状态、GameManager 相关逻辑。
- **2 线：关卡 / 场景 / 素材** — 背景、跑道、基地、资源接入、场景表现、`.scene/.prefab/.meta` 集成。
- **3 线：Boss / 演出 / 验证** — GOLIATH、Boss 演出、Timeline 检查、CI、自动验证。

这只是默认边界。若任务跨边界，先明确谁拥有最终集成权，避免两条线同时改同一核心文件。

## 4. 提交与 PR 纪律

每次提交应做到：

- Commit message 说明“改了什么”，不要只写 `update` / `fix`。
- 一个提交尽量只处理一个清晰目标。
- PR 描述至少写明：目的、主要文件、验证方式、已知风险。
- 如果修改了 Mission 01 的剧情时间点、Boss 交接、僚机事件等，必须同步检查 `tools/check-mission01.cjs` 是否仍然成立。

建议前缀：

- `feat:` 新功能
- `fix:` 修复
- `art:` 素材
- `test:` 验证
- `docs:` 文档
- `refactor:` 重构

## 5. 合并前最低验证

至少执行仓库现有快速检查：

```bash
node tools/check-project.cjs
node tools/check-mission01.cjs
```

若 GitHub Actions 有对应工作流，则以 CI 结果为准。涉及 Cocos 实际运行表现的修改，还需要至少一次 Creator / Web build 运行验证；纯静态检查不能替代视觉与交互验证。

## 6. 禁止事项

- 不允许在不知道最新 `main` 状态时直接覆盖核心文件。
- 不允许删除陌生脚本/资源，只因为当前分支没有使用它。
- 不允许重新生成已有 `.meta` UUID 来“解决问题”。
- 不允许用大范围重写来处理一个小冲突。
- 不允许未经确认改动其他工作线正在负责的系统边界。
- 不允许把生成目录、临时缓存、Creator 临时文件作为正常源码提交，除非仓库明确要求。

## 7. 冲突处理原则

遇到冲突时按这个顺序：

1. 先判断双方改动是否都需要保留。
2. TypeScript 冲突按逻辑合并并重新运行检查。
3. `.scene/.prefab/.meta` 冲突优先由该资源的当前负责人处理。
4. 无法确认 UUID / 引用正确性时，不要猜；保留分支，暂停合并并做 Creator 验证。

## 8. 当前协作原则一句话版

> 1 / 2 / 3 线可以同时开发、同时 push，但各推各的分支；验证通过后再集成到 `main`。Cocos 序列化文件默认单写者。
